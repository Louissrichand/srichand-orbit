# Orbit เฟส 5 — รายการเตรียมความพร้อม

ย้ายจาก "ไฟล์ JSON เดียวบน SharePoint" ไปเป็น Azure Static Web Apps + Azure Functions + Azure SQL
ออกแบบอยู่ใน `db/schema.sql` และ `docs/API.md` (รวมหัวข้อย้ายข้อมูล) เอกสารนี้คือสิ่งที่ต้องเตรียมและลำดับการเปิดใช้

## 1. สิ่งที่ต้องขอจาก IT

- [ ] Azure subscription ขององค์กร และสิทธิ์สร้าง resource group (แยก `orbit-staging` กับ `orbit-prod`)
- [ ] Region: Southeast Asia (สิงคโปร์) ทั้งชุด
- [ ] Azure Static Web Apps แผน **Standard** (ต้องใช้ API ที่ผูกมา, custom auth และ managed identity)
- [ ] Azure SQL Database แบบ **serverless** (ตั้งพักอัตโนมัติสำหรับ staging) ผูกกับ managed identity ของ Functions — ไม่เก็บรหัสผ่านในโค้ด
- [ ] Entra app registration: Redirect URI ของทั้งสองสภาพแวดล้อม (`https://<ชื่อแอป>.azurestaticapps.net/.auth/login/aad/callback` และโดเมนจริงถ้ามี)
- [ ] Admin consent สำหรับสิทธิ์ Microsoft Graph ที่ **เพิ่มขึ้น** จากปัจจุบัน (ระบุเป็นรายตัวตอนขอ เช่น อ่านโปรไฟล์/รายชื่อผู้ใช้, สิทธิ์ไฟล์ SharePoint ที่ใช้อยู่แล้ว) — **ต้องขอสิทธิ์จาก IT**
- [ ] (ภายหลัง ไม่บังคับ) การส่งแจ้งเตือนออกทางอีเมล/Teams: สิทธิ์ส่งเมลหรือ webhook ช่อง Teams — **ต้องขอสิทธิ์จาก IT** · ปิดไว้จนกว่าจะอนุมัติ
- [ ] การสำรองข้อมูล: point-in-time restore อย่างน้อย 14 วัน, สำรองระยะยาวรายสัปดาห์/รายเดือนตามนโยบายองค์กร, ทดลองกู้คืนจริงหนึ่งครั้งก่อนเปิดใช้
- [ ] การตรวจติดตาม: Application Insights + แจ้งเตือนเมื่อ error สูงหรือ timer function หยุด
- [ ] เครือข่าย/ความปลอดภัย: บังคับ HTTPS, ปิดการเข้าถึงฐานข้อมูลจากอินเทอร์เน็ตสาธารณะ (หรือจำกัด IP/Private endpoint ตามนโยบาย), เปิด auditing ของ Azure SQL
- [ ] **ผู้ดูแลระบบ**: ระบุชื่อทีม/ผู้รับผิดชอบที่ดูแลระบบ (ใครอัปเดต ใครรับแจ้งเหตุ ใครอนุมัติสิทธิ์) และผู้สำรอง

## 2. แผนทดสอบ (staging)

1. สร้าง resource group และฐานข้อมูล **staging แยกจาก production** ทั้งหมด
2. รัน `db/schema.sql` กับฐานเปล่า ต้องไม่มี error (รันซ้ำส่วน "Phase 5 sync" ได้โดยไม่พัง)
3. เอา **สำเนา** ไฟล์ JSON จาก SharePoint (ไม่ใช่ไฟล์จริง) ไปนำเข้า staging ตามหัวข้อ "ย้ายข้อมูลจาก SharePoint JSON" ใน `docs/API.md` แล้วทำ dry-run และตรวจสอบครบทุกข้อ
4. ทดสอบกฎสิทธิ์ตามตาราง "จุดรั่วที่ต้องเขียนเทสต์" ให้ผ่านทุกข้อ โดยเฉพาะ **โปรเจกต์ private** (ผู้ใช้ที่ไม่ใช่สมาชิก/ไม่อยู่ในทีมต้องได้ 404)
5. ให้ผู้ใช้ทดลอง 3–5 คน (ผสมบทบาท admin / member / guest / viewer) ใช้งานจริงอย่างน้อย 1–2 สัปดาห์: งาน ความเห็น อนุมัติ อัตโนมัติ เตือนฉัน รายงานสถานะ
6. ตรวจ timer function ตามรอบ (เตือน, งานเงียบ, อัตโนมัติตามเวลา, เลื่อนเตือน) ว่าไม่ทำซ้ำเมื่อรันชนกัน
7. ทดสอบกู้คืนฐานข้อมูลจากข้อมูลสำรอง และทดสอบย้อนกลับไปใช้แอปเดิม

## 3. ลำดับการเปิดใช้งานจริง

1. **ทีม BD ก่อน** (ข้อมูลไม่ลับ) — ตัดข้อมูลนอกเวลางาน, ตรวจสอบหลังนำเข้าตามหัวข้อย้ายข้อมูล, เปิดให้ใช้ แล้วเก็บปัญหา 1–2 สัปดาห์
2. ทบทวนผล: ความเร็ว ข้อผิดพลาด คำร้องจากผู้ใช้ ค่าใช้จ่ายตามจริง
3. **ทีมที่มีข้อมูลลับ** — เปิดได้ต่อเมื่อยืนยันแล้วว่าการบังคับโปรเจกต์ private ที่ฐานข้อมูล/API ถูกต้อง
   (ผลเทียบ `fn_VisibleProjects`/`fn_VisibleTasks` กับแอปเดิมตรงทุกแถว และเทสต์ข้อ 11–12 ผ่าน) โดยมีผู้ดูแลระบบอีกคนตรวจซ้ำ
4. ทั้งองค์กร
5. หยุดใช้ไฟล์ JSON เดิม (เก็บสำรองอย่างน้อย 90 วัน) และปิดสิทธิ์เขียนไฟล์นั้น

## 4. เงื่อนไขหยุดหรือย้อนกลับ

- เจอโปรเจกต์ private ที่คนนอกเห็นได้ แม้เพียงรายการเดียว → ปิดการเข้าถึงทันทีและกลับไปใช้แอปเดิม
- จำนวนแถวหรือเนื้อหาหลังนำเข้าไม่ตรงกับต้นทาง → ห้ามเปิดใช้ แก้ตัวนำเข้าแล้วเริ่มใหม่
- timer function ทำงานซ้ำหรือหยุด → ปิดงานนั้นและแก้ก่อนเปิดทีมถัดไป
